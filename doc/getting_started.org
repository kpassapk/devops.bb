* Intro

In this guide, we will use a sandboxed agent to provide an assessment on the disk usage of your (local) machine. But wait - you say - this can't possibly work, because the agent can't see your local machine. It's in a Docker container. It can only see its local file system. How is it going to work?

Here's how it's going to work:

1. You (the "operator") will select a =.org= file to serve as your "workbook". This is a scratch file shared between you and the agent.
2. You start a specially provisioned Docker container. Your project and the container share a [[file:../sandbox/Dockerfile::WORKDIR /work][/work]] direcotry and a =/feed=. The feed directory is the "sink".
3. In Emacs, you /attach/ your workbook using =devops-bb-sandbox-attach=, and selecting the container you just launched as the sink.
4. You launch Claude in the sandbox, and tell it to use the [[../sandbox/skills/devops-link/SKILL.md][devops-link]] skill.
5. You ask the agent a question. (Typey typey.)
6. The agent will think about what data it needs from your machine. It writes a code block to get that info, in [[devops.el][https://github.com/kpassapk/devops.el]] syntax.
7. You execute the code block.
8. The agent gets notified via the =/feed=, and reads the command output. (From an async session pool provided by =devops.el=).
9. The agent interprets the output and wirtes the result in your workbook.

From your (the operator's) point of view, you are seeing text pop up in your workbook, executing code blocks, and reading the output. The agent is busy running commands in its sandbox and asking you for stuff.

This example uses disk space; a more useful example might use the AWS or Github ClI, the =vercel= CLI, something like that.

To summarize, here is what each party owns:

*Operator*:
- filesystem
- CLIs  

*Agent*:
- workbook
- coding: file read + write, tools like python, grep

*Both*:
- the workbook
- the work/ directory containing your workbook

Prompt: 
#+begin_example
  Use the devops-link skill. I want a summary of which of my host's filesystems are over
  50% full. Get df -h from the host through a block in /work/trial.org, then write/work/summary.py that parses that output, and test the script yourself.
#+end_example

6. What to look for:
- Claude runs devops-bb status, starts follow --wake under Monitor, and checks modified before writing the workbook.
- Your buffer reloads with Claude's block in it.
- Running the block shows the posframe with the notice "not run since attach", and d opens the diff.
- Claude sees the run, reads it with run-output, writes and tests summary.py itself, and asks for no block to do that.
- If Claude adds a block that runs the script on the host, the prompt shows "files changed … summary.py (new)", and d shows the file's diff.
- Re-running an unchanged block runs it without a prompt.

7. Try to break it. Run these from a second terminal into the container: docker exec trial-box sh -c '…'
- touch /work/.envrc → the mode line says sandbox: SUSPENDED and runs are refused. rm /work/.envrc and it resumes.
- ln -s /etc /work/etc → suspended as well. Remove it.
- Append a block with :var x=(shell-command "touch /tmp/pwned") to trial.org. Running it should be refused with "elisp in header", and /tmp/pwned should not exist on your host.
- Edit a block you already ran, then run it → it prompts with "changed since you ran it: +n/-m".

8. Detaching and quitting:
- M-x devops-bb-sandbox-detach, then docker exec trial-box devops-bb status → "attached":false. Claude's follow should print a "detached" notice.
- Attach again, then quit Emacs → status should again show "attached":false. This is the interactive-quit check from PR 7.

9. Clean up: docker rm -f trial-box and rm -rf ~/sandbox-trial.
