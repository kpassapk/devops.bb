* Background

Business reason: we work with servers and systems containing sensitive data.
Users have a significant access scope via CLIs and Tailscale SSH.

Best practices for security dictate that agents should be running in a
sandbox, where they cannot access the user's file system or other
credentialed services. "Sandboxes" and other controls built into
agent harnesses are fragile, and the agent can overcome them easily. (I think.)

We believe the only way to run agents is in a separate machine or container.
Here, the agent writes files, runs local tools (in the sandbox, for example
finding a pattern using grep, compiles and runs code, etc.

Yet some of the most powerful use cases for agents involve real-world
information systems, provider APIs, and deployed apps.

When the agent needs something from the outside world, it should ask
the user to run a command. This could be during regular coding or an
incident.

During regular coding, this could be an AWS or Cloudflare command,
running an infrastructure runbook, downloading data from a shared
development system, looking at logs, doing discovery on an already
running system or API, or a third party API; or getting something from
the company's ERP. You would run these commands from a remote development
=#+TARGET= machine. Tailscale ACLs gate access.

During an incident, this could be running a command in a production
server to determine system status or find root cause. You would run
these commands in an ops-specific target machine, or via a bastion
host. (Again secured with Tailscale.)

Copying and pasting commands and results is a terrible workflow,
especially in demanding situations like an incident, when we may be
running dozens of code blocks in quick succession.

Our approach leverages Emacs's org mode and its org-babel executable notebooks.
Devops.el contains some basic primitives like =TARGET= selection. devops.bb's
Emacs side (=emacs/=) logs what the operator does, and answers the
=devops-bb= commands over =emacsclient=.

This project implements a more highly opinionated flow using babashka tasks.
We would like to use this as a dependency in other projects' =bb.edn= tasks.

* Spec

** Goal

Claude Code runs in a *sandbox* and still works the devops-bb loop:

- it writes and edits its one workbook;
- the operator runs the blocks in Emacs, on the host;
- Claude follows each run and reads its output;
- it *never* uses a credentialed resource itself, and holds nothing
  that could reach the host's Emacs, servers, or other credentialed
  tools.

A *credentialed resource* is anything the operator can reach and Claude
must not: a server over ssh, a CLI with a profile or token (=aws
--profile prod=, =kubectl --context=, =gh=, =psql=), git with push
access. A target is a credential, not only a host. The workbook is the
one way to use them, each use reviewed by the operator.

*Anything that needs no credential, Claude does itself, in the
sandbox*: edit code, =bb test=, a REPL, lint, build, =grep=. Only the
credentialed step goes through a block. This is the loop for all
development, not only incidents: repos, other checked-out projects,
ephemeral instances.

The sandbox is any place Claude can be put, not only a devcontainer:

| Sandbox                  | Workbook dir reaches the host by          | Feed reaches it by          |
|--------------------------+-------------------------------------------+-----------------------------|
| local container          | bind mount (rw) of the workbook dir       | bind mount (ro) of the feed |
| Tailscale node / SSH box | =devops-bb-sandbox-pull=, host-driven rsync | host pushes over =--ssh=    |

Either way the workbook dir is on the host's disk, so the host can
check and hash it (below). TRAMP is not supported: attach refuses a
remote =buffer-file-name=.

*devops-bb in the sandbox* needs babashka 1.13.226 or later (on
1.12.200 the =:exec-fn= tasks print nothing and exit 0) and =git=:
bb 1.13 resolves =bb.edn='s git dep (charm.clj) with =git=, no Java.
Resolve deps when the image is built, so the running sandbox needs no
egress for them. Claude's user is not root and does not own the feed;
the publisher writes it as root (=docker exec -i -u root=) or as the
node's =feed= user. A container run, from PR 9's check:

#+begin_example
docker run -d --name BOX --user 1000:1000 -e HOME=/tmp \
  -v "$WB_DIR":/work:rw -v "$FEED":/feed:ro IMAGE sleep infinity
devops-bb publish --via "docker exec -i -u root BOX" --to /feed \
  --map "$WB_DIR=/work" --name wb    # or --to "$FEED" for the ro mount
#+end_example

The workflow is the library's main one, so the design bends devops.bb
to it instead of wrapping it with scripts in each project
(replaces steps 4-5 of the infra-devcontainer workbook).

** The one idea

=devops.bb= currently answers from two sources on the host: the
execution log (a file) and Emacs (=emacsclient=). The sandbox can
reach neither.

devops.bb writes the log too (=devops-bb-log-mode=,
=emacs/devops/bb/log.clj=), so the feed is made where the events
happen, in the operator's Emacs, instead of by reading the log back:

- *producer*, in the host's Emacs: a workbook buffer attached to a
  sandbox gets a *subscriber* to the log's events. It adds each
  finished run's output and writes the line to a child =devops-bb
  publish= on stdin. The child pushes a *feed*, a self-contained
  directory of plain files, to a *sink*.

- *consumer*, in the sandbox: with =DEVOPS_BB_FEED=DIR=, the same
  commands (=status=, =follow=, =run-output=, =modified=) read the feed.
  They never start =emacsclient=.

Data flows one way, host → sandbox. The sandbox has no credential for
the host.

** Threat model: the operator is the boundary

The read side is closed: the feed flows one way and carries no
credential. The write side is not, and cannot be: Claude writes the
files the host's Emacs loads and runs. Claude may propose any command;
the operator decides what runs. Everything below exists to make that
review real: the operator sees what will actually run, where, and what
changed since they last said yes, and nothing Claude writes runs
without that.

Ways in, and what closes each:

| Claude writes                                         | Closed by                                  |
|-------------------------------------------------------+--------------------------------------------|
| a block, or a changed block                           | confirm every run (Review)                 |
| =:var x=(elisp)=, =#+PROPERTY header-args=            | elisp in a header value is refused before org evaluates it (Review) |
| a noweb reference or call                             | prompt shows references expanded, calls as written, with a notice |
| =#+TARGET=, static or dynamic                         | prompt shows resolved target; change re-prompts |
| =analyze.py=, =bb.edn= run by an approved block        | the workbook dir is in the fingerprint     |
| commits, pushed by an approved block                  | bundle SHAs in the fingerprint; prompt shows the log (Code) |
| a malicious repo config or hook                       | the host never runs git in Claude's repo; bundle only |
| =# Local Variables:= / =eval:=                        | =hack-local-variables= advice              |
| =.dir-locals.el=, =.git/= (=core.fsmonitor=), =.envrc=, symlinks | dir check suspends the buffer     |
| a symlinked feed dir on an ssh node                   | =feed= user, symlink refusal (Sinks)       |
| (on the node) the operator's forwarded ssh-agent      | =--ssh= forces forwarding off (Sinks)      |
| (on the node) a direct route to the servers           | tailnet ACL, checked in step 4             |
| (in the sandbox) a credential                         | none provisioned: no =~/.ssh= keys, =~/.aws=, =gh= token, origin creds; checked in step 4 |
| =#+TARGET: x /aws:prod-admin:=, any profile the operator has | every scheme must have =:allow=; attach and each run refuse otherwise (Review) |

Feed output is server output, and may carry injected text; the skill
tells Claude to treat it as data, not instructions.

** Code: the repo lives in the sandbox

Developing in an existing repo, aly-clojure say, does not put the repo
in the workbook dir: its dot-paths (=.git=, =.github=, =.clj-kondo=)
would suspend it, hashing =target/= on every confirm is slow, and the
operator would be approving =bb test=, which needs no credential.

- *Claude's own clone, in the sandbox.* Inside the container (or a
  separate rw mount, never the workbook dir), or on the node. Claude
  edits, tests and commits there freely.
- *Seeded from the host.* A block the operator runs makes =git bundle
  create WB/<repo>.bundle --all= in the host checkout; Claude clones
  from the bundle. The sandbox never needs read credentials for
  origin.
- *Back as a bundle.* Claude runs =git bundle create
  /work/<repo>.bundle origin/main..HEAD= into the workbook dir; the
  mount or pull brings it. A bundle is a regular file, which the dir
  check allows, and pure objects and refs: no config, no hooks, no
  =fsmonitor=. The host never runs git inside a repo Claude controls,
  and Claude never gets the host's working tree.
- *Fetched into a namespace.* =git -c transfer.fsckObjects=true fetch
  WB/<repo>.bundle 'refs/heads/*:refs/sandbox/*'= in the host
  checkout, never into =refs/heads=.
- *Reviewed at push.* The credentialed step is a block: =git push
  origin refs/sandbox/feature:refs/heads/feature=, or =gh pr create=.
  The fingerprint includes the bundle's commit SHAs, so a new bundle
  re-prompts, and a notice shows =git log --stat
  origin/main..refs/sandbox/feature=. Code is reviewed as commits when
  it leaves, not as a dir diff on every run.

The workbook dir stays small: the =.org=, =:file= outputs, bundles,
and the occasional script a block runs. Its whole-dir fingerprint
(Review) covers only that.

** Review: confirming each run

devops.bb owns the policy; [[file:~/src/github.com/kpassapk/ob-confirm-posframe/ob-confirm-posframe.el][ob-confirm-posframe]] owns the display,
through generic extension points. =devops-bb-sandbox-attach= refuses
unless =ob-confirm-posframe-mode= is on: a bare =y/n= shows neither
headers nor diffs.

*Every run is confirmed, unless unchanged.* In an attached run the
confirm decides by a *fingerprint* of the run, sha256 of: lang; the
body, references expanded and calls as written; the processed params,
inherited ones included, sorted, with =:dir= expanded (without file
handlers) and the pool slot =<N>= stripped from =:session=; the
resolved target (=devops--block-target=, TAG and TARGET, a dynamic
target's value included), the session and =devops-target-env=; and
(path, size, sha256) of every file in the workbook dir except the
=.org=. A fingerprint the operator confirmed and that then ran
(recorded in =org-babel-after-execute-hook=, so a run that failed after
the yes prompts again) skips the prompt; anything else prompts.
Re-running an unchanged diagnostic stays one keystroke; any edit Claude
makes, to the block or to a file beside it, prompts once with the
diff. Hashing is not cached: 43 files, 1.7 MB take ~17 ms (PR 8's
spike).

devops.el resolves =#+TARGET= in its =org-babel-execute-src-block=
advice, before org's confirm, so by then =params= holds the injected
=:dir= (possibly relative, as written) and =:session=: the fingerprint
and the prompt read them there. The target comes from devops.el's
private =devops--block-target=; it should become public (only
=devops-block-session= is today).

*The confirm is advice, not a wrapper on =org-confirm-babel-evaluate=.*
Org calls a function there as =(LANG BODY)= with the body already
expanded, which runs noweb calls before any prompt, and without INFO.
So =:around= advice on =org-babel-check-confirm-evaluate= decides for
attached runs: it calls the original with the variable bound to t (so
=:eval no= and =:eval query= keep their meaning) and returns t only for
a confirmed fingerprint. Unattached buffers never reach it; the user's
own setting applies there unchanged.

*What the prompt shows*, via ob-confirm-posframe:

- =ob-confirm-posframe-header-functions=: target and session, plus
  =target TAG TARGET · ENV=. It follows =:dir= on the line and is cut
  at the posframe's width when =:dir= is long, so a scheme's credential
  is also a notice.
- =ob-confirm-posframe-notice-functions=: highlighted lines above the
  body, each a string or =(ob-confirm-posframe-notice LINE DETAIL)=.
  devops.bb adds "not run since attach", "changed since you ran it:
  +n/-m", "files changed since you last ran a block: =a.py +2/-0 (new)=,
  …", "noweb call: =name()=", "resolves target =TAG= for =OUTER=",
  "target changed: =A= → =B=" and "credential: target =/aws:dev: ·
  AWS_PROFILE=dev=". Diffs are =diff -u=, kept behind =d=.
- =ob-confirm-posframe-expand-noweb=: the body with noweb references
  expanded, the text that runs. A call =<<name()>>= is shown as
  written, never expanded: =org-babel-expand-noweb-references= runs it
  (PR 6's spike).
- =d=: every notice with its detail, a multi-file =diff-mode= buffer,
  in a window; =q= returns to the prompt.
- The advice is at depth -90, outside devops.el's, so a dynamic
  target's block prompts inside the chain of the block the operator
  ran: =check-disk › pick-host=. Org resolves =:var= references before
  it confirms, so prompts come innermost first.

*Elisp in a header is refused, not shown.* Org evaluates elisp header
values (=:var x=(…)=, =:dir (…)=, inherited ones from =#+PROPERTY= or a
property drawer) when it processes params, which is before the confirm
(PR 6's spike), so no prompt can guard it. Two layers, for a run from
an attached buffer and for files that run visits for a reference:

1. *Raw check.* Advice on =org-babel-get-src-block-info= and
   =org-babel-lob-get-info= (when they evaluate) checks each source org
   reads separately, since org evaluates each as it parses it, before
   merging: the defaults (inline, per language, lob), =header-args= and
   =header-args:LANG= properties (=#+PROPERTY= and drawers, inherited),
   =#+HEADER= lines, the block line, and a call's inside and end headers
   and arguments. Advice on =org-babel-ref-resolve= checks reference
   arguments and =[headers]=; noweb calls' arguments are checked when
   the review expands the body, before the prompt. A value is elisp
   when it starts with =(=, ='=, =`= or =[=; a =:var='s right-hand side is
   checked recursively; =*this*= is allowed. The refusal is a
   =user-error=, "elisp in header =:var x=: a sandboxed workbook may not
   evaluate header values", before any prompt and before devops.el
   resolves a target.
2. *Backstop.* A guard on =org-babel-read= refuses any lisp evaluation in
   an attached run until that run is confirmed. Every
   =org-babel-execute-src-block= and =org-babel-ref-resolve= starts
   unconfirmed; only a yes sets it.

The operator's own non-string =org-babel-default-header-args= are
trusted. =:dir 'attach= is refused: it looks like elisp.

*Org creates =:output-dir= while only reading a block's info*, even
without evaluating, so before the confirm. Advice on
=org-babel-generate-file-param= stops it for a dir outside the
workbook dir.

*Dynamic targets* stay: targets may be checkouts and ephemeral
instances. devops.el binds a public =devops-resolving-target=, =(TAG
. REF)=, while =devops--target-from-ref= runs, for the notice. The
target's block is fingerprinted like any other; its *output* is not
trusted that way: it is part of the main block's fingerprint, so a new
instance re-prompts every block under that heading once.

*Scheme targets* (devops.el's =devops-target-schemes=, =/aws:prod:=)
are credentials. The prompt and the fingerprint use
=devops-target-env=: =target /aws:prod: · AWS_PROFILE=prod · unset
AWS_ACCESS_KEY_ID …=. In an attached buffer *every scheme must have
=:allow=*: without one, Claude can name any profile the operator
has. Attach refuses when any entry of =devops-target-schemes= lacks
=:allow=, since Claude can add a =#+TARGET= at any time; and the
confirm function refuses a run whose resolved target is a scheme
without =:allow=, since the map can change after attach: "scheme =aws=
has no :allow; a sandboxed workbook may only name allowed credentials".
devops.el's own =:allow= check then rejects an ARG outside the list.

*State lives in a global registry*, ={base-buffer → attachment}=, not
in buffer-locals: =M-x revert-buffer= runs =normal-mode=, which kills
buffer-locals and then reads =# Local Variables:=. The registry holds
the subscriber, the publisher, the confirmed fingerprints, the last
confirmed text of each block and a snapshot of the workbook dir (for
the diffs). Detach clears it.

- =:around= advice on =hack-local-variables= binds
  =enable-local-variables=, =enable-local-eval= and
  =enable-dir-local-variables= to nil for an attached buffer, and for
  files its runs visit. Attach re-runs =normal-mode= if the buffer had
  already read file-local or dir-local variables. The =mode:= cookie is
  still honoured by =set-auto-mode=.
- vc is off for attached buffers (=vc-handled-backends= nil around
  =vc-refresh-state=, vc props cleared at attach), so Emacs never runs
  =git status= in the dir.
- After a revert that changes keyword lines, =org-mode-restart=, so
  =#+PROPERTY= and =#+STARTUP= caches match the disk. Affiliated
  keywords (=#+NAME=, =#+RESULTS=, =#+CALL=) don't count. Safety does not
  depend on it: the fingerprint uses the processed params.
- Revert with =preserve-modes= (auto-revert) reads no local variables
  (PR 8's spike); the advice covers it anyway, and a test does.

*Emacs's own files stay out of the dir.* The lock file =.#wb.org= is a
dotfile symlink, so the operator's first edit would suspend the
buffer, and auto-saves (=#wb.org#=) and backups (=wb.org~=) would change
the fingerprint. Attached buffers set =create-lockfiles= nil (dropping
any existing lock) and keep backups and auto-saves under
=~/.emacs.d/devops-bb-sandbox/=.

*The workbook dir is checked* on attach (which it refuses), after every
revert, on every run and on every confirm. Any regular file and
subdirectory is allowed: Claude writes code. A dotfile or dot-dir at
any depth (=.git=, =.dir-locals.el=, =.envrc=, …), a symlink (read with
=file-attributes=, never followed, dangling ones included) or a special
file *suspends* the buffer: every run is refused with "sandbox dir has
=.git/=: remove it to continue", the mode line says =sandbox:
SUSPENDED=, and the buffer resumes once the check passes. The check is
time-of-check: Claude could add a symlink between the check and the
run. =:file= and =:output-dir= may not be absolute, contain =..= or be
elisp, and, resolved against the block's =:dir=, must land inside the
dir; so a block on a remote target cannot write =:file=. The README
says to keep LSP auto-start off in sandbox dirs: clojure-lsp evaluates
=bb.edn= and =deps.edn= on visit, which no check can catch.

** Events: one emit, many subscribers

=log.clj= builds an entry and appends it to the log file. Split that:
=emit= builds the entry and hands it to each subscriber, and the log
file is one subscriber.

- *Log subscriber*, global: appends to =devops-bb-execution-log=, the
  same lines as today. They stay notifications, with no output,
  =#+RESULTS= or diff, and the file stays shared by every Emacs and
  workbook.
- *Sandbox subscriber*, one per attached buffer, cljbang in
  =sandbox.clj=: gets only the entries emitted from its buffer. For a
  =result= entry it takes the run's output from the session and sends
  the entry with an =output= field. For a sync =execute= (status not
  =running=; not "no =id=", since =block-output= can return an old async
  run of the same body) it makes up a UUID and sends =#+RESULTS= as the
  output (Caveats).

=(devops-bb-log-subscribe F &optional BUFFER)= and
=devops-bb-log-unsubscribe= register F, called with the entry (a
cljbang map), globally or for BUFFER's base buffer. The tables are
globals, so a revert keeps them. =emit= does nothing unless
=devops-mode= is on and someone listens. Only the log subscriber needs
=devops-bb-execution-log=; =devops-user-run-p= applies to run events
(=execute=, =result=), as before: =tangle= and =drift= are user-only
already, and edit events are not runs.

Dispatch is by *base buffer*, not by =file=, so there is no path filter
to get wrong: =emit= looks up =(or (buffer-base-buffer)
(current-buffer))=, so a run from an indirect buffer
(=org-tree-to-indirect-buffer=) reaches its workbook's sandbox. Its
async result is inserted with the indirect buffer current (PR 7's
spike). Entries from an indirect buffer carry its =buffer= name and a
=line= relative to its narrowing; the log keeps them so, and the
sandbox subscriber converts =line= to the line in the file. Killing an
indirect buffer whose base has unsaved edits emits a =kill= entry; the
subscriber drops it, or feed-mode =modified= would say false while the
workbook has unsaved edits. Killing the base detaches, from
=kill-buffer-hook= at depth 90, after the base's own =kill= entry. A
subscriber that fails is reported in =*Messages*= as =devops-bb-log: F
failed on EVENT: MSG= and does not stop the others, the log, or the
block run; so is a failed log write.

*One run, by ID.* The =result= entry is emitted inside ob-comint's
process filter. =devops-bb-scripting-run-output= scans the whole
session for every run; the subscriber instead uses a new
=devops-bb-scripting--run=, which searches the start and end markers
of that ID only, and =run-output= uses it too. The subscriber takes at
most =--max-bytes= × 2 of output, head and tail
(=devops-bb-scripting--head-tail=), so a huge output never leaves
Emacs, and marks a cut answer =truncated= with the full =lines= and
=bytes=, which the publisher keeps; the publisher's cap stays the
exact, tested rule. =--run= searches forward from the top, so the
latest run still costs a read of the whole buffer (~5 ms per 0.5 MB);
the old scan grew with the square of the runs (2.5 s at 1000 runs).
=devops-bb-scripting-sessions= still uses the old scan.

*Emacs never waits.* The split, JSON lines on stdin the only interface:

| Emacs (cljbang): =log.clj=, =sandbox.clj=      | bb: =publish.clj=, =feed.clj=                 |
|------------------------------------------------+-----------------------------------------------|
| =emit= → subscribers, by base buffer           | stdin → queue, always drained                 |
| output by ID, rough head/tail cap              | exact cap, =seq=, =--map=, =status.json=       |
| =status= line on rename                        | sinks: =put=, =append=, retry, heartbeat      |
| child process, sentinel, mode line             | nothing about Emacs or org                    |
| review: fingerprint, dir check, notices        |                                               |

The log keeps its promise of no output. The feed carries output, but
only for the one workbook and the one sandbox it is bound to.

** One workbook per sandbox

A sandbox is bound to exactly one buffer, in one Emacs. The operator
can have many sandboxes at once, one per workbook, all from the same
Emacs.

*Attaching.* The operator attaches a workbook from its buffer with
=devops-bb-sandbox-attach= (cljbang, =emacs/devops/bb/sandbox.clj=). It
asks for a sink by name from =devops-bb-sandbox-sinks=, a defcustom
=((NAME . PLIST) …)= with =:to= (required), =:via= or =:ssh=, =:map= (an
alist of host dir → sandbox dir), =:max-lines= and =:max-bytes=, and a
feed name; starts =devops-bb-sandbox-publish-command= (default
=devops-bb publish=) with those flags and =--name= as a child process
with stdin a pipe; and registers the base buffer. One sink serves one
live attachment. =devops-bb-sandbox-detach=, killing the buffer, or
quitting Emacs closes stdin: the publisher pushes what it has, marks
the feed detached, and exits. Killing a buffer with unsaved edits
sends its =kill= event before stdin closes. Attaching a buffer that is
already attached asks to replace its sink.

*Quitting Emacs.* Emacs SIGHUPs its children on exit, so the
publisher never flushed (PR 7's spike). It runs as =sh -c "trap ''
HUP; exec \"$@\""=, and a =kill-emacs-hook= closes each publisher's
stdin and waits up to =devops-bb-sandbox-quit-timeout= (2 s) for it.
The publisher still flushes past that. A sink that hangs at EOF keeps
the publisher waiting forever; nothing kills it yet.

Attach refuses when =ob-confirm-posframe-mode= is off, when
=buffer-file-name= is remote, when the dir check fails, or when a
scheme in =devops-target-schemes= has no =:allow= (Review). It
warns when the workbook's dir holds other =.org= files: one dir per
workbook.

*A dead publisher is loud.* A process sentinel watches the child. When
it dies the mode line says =sandbox: DEAD= and attach offers to
restart. A restart is a new attach: new =started=, =seq= from 1, and
=follow= tells Claude the feed restarted. No replay.

*One directory per workbook.* The sandbox gets the workbook's own
directory, rw, holding only that workbook, its =:file= outputs and the
code Claude writes: =work/<denote-id>/=, or any dir the operator picks.
Not the file: a file bind mount is pinned to an inode, and the first
save by rename leaves the sandbox on the old one. Not =work/=: the
siblings' =#+RESULTS= hold past server output. Attached buffers get
=backup-by-copying= anyway, for git and rsync, reapplied from
=after-change-major-mode-hook= so a revert keeps it; the mode line
entry =sandbox: FEED= is an =(:eval …)= in =mode-line-misc-info=, read
from the registry. The feed is a separate
ro mount, never inside the workbook dir:
=-v $WB_DIR:/work:rw -v $FEED:/feed:ro=.

*Remote sandboxes: pull.* =devops-bb-sandbox-pull= runs =rsync -r
--no-links --exclude '.*'= from the sandbox into the local workbook
dir: on a timer while attached, and right before each confirm, so the
prompt reflects the latest. Symlinks and dotfiles never arrive (PR
10's spike). macOS's openrsync (protocol 29) is acceptable for this
pull: the flags hold with it, and the README names it. git by hand
stays possible; TRAMP is not supported.

*The feed name is the operator's.* It is asked at attach (default: the
file's base name), passed as =publish --name= (default there: the
basename of =--to=), and goes in =status.json= and on every event as
=feed=. It names the attachment, not the file, and stays the same
across renames; a NATS subject later (below). It is never read from
the workbook: Claude writes the workbook.

*The sink is the operator's.* It is set in Emacs, never in the
workbook: Claude writes the workbook, and a sink written there could
point the push, with the operator's ssh credentials, anywhere.

*Renames.* Nothing to do. The subscriber is bound to the buffer, and
each entry reads =file= when it is emitted, so after
=set-visited-file-name= or a denote rename the next event carries the
new path. =sandbox.clj= writes a =status= line,
={"event":"status","file":…,"devops-mode":…}=, straight to the
publisher: at attach, from =after-set-visited-file-name-hook=, and
before an entry whenever the file differs from the one it last sent,
so =status.json= follows too. It is not an event.

*Shared shell sessions.* devops.el names sessions by target
(=devops:web-1 /ssh:web-1:=), so two workbooks on the same target share
a shell. The feed is per run and leaks nothing, but shell state (cwd,
exported variables) carries over between workbooks in different
sandboxes. The README says so; per-workbook session names are later
work.

** The feed

#+begin_example
FEED/
  status.json         feed name, workbook, devops-mode, attached, publisher heartbeat
  events.jsonl        the events, paths mapped, numbered by seq, appended in order
  outputs/<id>.json   run-output answer, one file per finished run
#+end_example

The publisher reads JSON lines on stdin, one at a time, in order. It
reads no log and asks no Emacs: it has no =--server= or =--file=, and
never runs =emacsclient=. What it pushes, Emacs handed it. Rules:

1. *Output before event.* A line with =output= becomes
   =outputs/<id>.json= first, then the event, without =output=, is
   appended to =events.jsonl=. A consumer that sees the event can read
   the output at once, so there is no =not-found= retry. =output= is the
   full answer map, or text, from which the answer is built with the
   entry's =session=, =status=, =id= and =input= (then dropped from the
   event). =output: null= writes no file. An id that is not a UUID is
   dropped with a warning, so it never becomes a path.
2. *Atomic.* Write to =.tmp=, rename. =events.jsonl= is append-only.
3. *Numbered.* Each event gets =seq=, 1, 2, … from the attach, so
   =follow= can resume after a seq. Attaching starts a new feed:
   =events.jsonl= starts empty, =seq= at 1, and =status.json='s
   =started= says when. The writer empties =events.jsonl= before it
   writes the new =status.json=, so a follower never takes old events
   for the new feed.
4. *Heartbeat.* =status.json= carries =publisher-time=, refreshed
   every few seconds, so the sandbox can tell a quiet workbook from a
   dead publisher, and =attached=, false once stdin closes. It names
   the =feed= and the =workbook= (mapped path), and =queued=, the
   events not yet pushed, so =follow= can say "publisher is N events
   behind" instead of only "stale", and =dropped= (rule 8). The
   workbook comes from the first =status= line, or until then the
   first event's =file=. It does not carry =execution-log=: the log's
   path is the host's business. The heartbeat is every 3 s.
5. *Path mapping.* =--map HOST=SANDBOX= (repeatable; the longest
   prefix wins, on a path boundary) rewrites =file= and the workbook
   (=buffer= stays). Entries carry host paths; a sandbox that mounts elsewhere
   still resolves the workbook in =status=, =follow= and =modified=.
   Same absolute path (no =--map=) remains the easy case for
   containers.
6. *Outputs are JSON.* =outputs/<id>.json= is the =run-output= answer
   exactly as host mode prints it (={session, status, id, input,
   output}=). Feed mode prints the file as is, so both modes give the
   same shape and the skill does not need a separate path for feed mode.
   One file carries status and output together, so one rename keeps it
   atomic. For grep in the sandbox: =jq -r .output outputs/ID.json=.
7. *Capped.* An =output= over 500 lines or 64 KB, whichever comes
   first, keeps its first 250 and last 250 lines (each half within
   (max-bytes − 64) / 2 bytes; a line too long for its half is cut
   short and counted as cut), with one marker line between them: =[…
   N lines cut …]=. The
   answer then carries ="truncated": true= and the full size,
   ="lines"= and ="bytes"=. =--max-lines= and =--max-bytes= change the
   caps; they are given at attach, like the sink. A run's start says
   what it is and its end how it went, so both are kept. The cap
   protects the sink and Claude's context; host mode's =run-output= is
   not capped.
8. *Never blocks Emacs.* A reader thread drains stdin into an
   in-memory queue, capping each line as it takes it; a writer thread
   pushes to the sink in order, retrying with backoff (100 ms up to
   5 s), and also starts the feed, so a sink that hangs at startup
   still never blocks stdin. A hung ssh never fills the pipe, so
   =process-send-string= in ob-comint's filter never blocks the
   operator's Emacs (PR 3's spike: a child that stops reading froze
   Emacs for 10 s). Memory stays bounded by count too: past 10000
   unpushed events the reader drops lines and counts them in
   =dropped=, rather than block stdin.
9. *Retries are safe.* =put= is a rename. A retried =append= may land
   twice; the reader skips any event whose =seq= is not above the last
   it saw.

** Sinks: where the feed goes

Two verbs, =put(path, bytes)= (replace atomically; =path= is relative
to =--to=) and =append(line)= (one JSON line, always appended to
=events.jsonl=), and two options, =--ssh= and =--via=:

| Sink                  | Flags                                          |
|-----------------------+------------------------------------------------|
| local directory       | =--to /path/feed= (dev and tests; no isolation by itself) |
| container (mount)     | =--to /path/feed=, mount that dir ro           |
| container (no mount)  | =--via "docker exec -i box" --to /feed=        |
| Tailscale / SSH node  | =--ssh feed@node --to /home/feed/feed=         |

With =--via CMD= (split into shell words) and =--to TO= (absolute),
each push runs =CMD sh -c SCRIPT=, paths quoted into SCRIPT. Anything
that runs a command somewhere fits: =docker exec -i=, =podman exec -i=,
=kubectl exec -i=. No TRAMP re-implementation. SCRIPT never waits for
EOF: =docker exec -i= sometimes loses an EOF sent before the command
starts, and a =cat= then hangs in the container for good, killing the
host side does not stop it (PR 9). So SCRIPT reads the event line with
=read -r=, then the output, sent last, with =head -c N= and a size
check. It removes =F.tmp=, writes it under =set -C=, and renames it to
=F=; for a result it renames before it appends. It exits 3 when =TO=,
=TO/outputs=, =F= or =F.tmp= is a symlink, and refuses feed paths with
=..= or a leading =/=. A command that doesn't finish in 30 s is killed
and retried. =--via "ssh …"= does not work: ssh re-joins and re-parses
the remote command, so SCRIPT would need quoting twice. ssh is =--ssh=
only.

*The push is a connection into a machine Claude controls*, so for ssh
it is built in, not left to the operator's config:

- =--ssh HOST= runs =ssh -T -o ForwardAgent=no -o ForwardX11=no -o
  ClearAllForwardings=yes -o PermitLocalCommand=no HOST …=. A
  =ForwardAgent yes= in =~/.ssh/config= (or =Host *=) would otherwise
  hand the node a live socket to the operator's agent, and Claude could
  =ssh web-1= with it. =--ssh= quotes SCRIPT for the remote shell
  itself.
- *A =feed= user.* The README sets up a =feed= account on the node
  that owns the feed dir; Claude's user may read it, never write it.
  Otherwise Claude can replace =outputs/= with a symlink and the push
  writes, as the push user, wherever it points.
- The remote script refuses to write when =TO=, =TO/outputs= or the
  target is a symlink (=[ -L … ]=), as defense in depth.
- *Tailnet ACL.* Claude's "no path" to the servers is as real as the
  ACLs: the node gets a tag (=tag:sandbox=) with no grants to servers,
  and step 4 checks it from the node.

*One round trip per result.* A result is a =put= and an =append=. Over
=--ssh= or =--via= the publisher sends both in one command, so a run costs one
connection, not two: =CMD sh -c '…'= reads the event line, then the
output, from stdin, and does the rename before the append, keeping
"output before event". The heartbeat is a =put= of its own, every few
seconds. A =docker exec= costs ~55 ms (PR 9's spike), so one command
per result keeps up. For ssh, the README recommends =ControlMaster= so each command
reuses one connection.

Why push, not pull: a pull would give the sandbox a way into the host.
Push needs host → sandbox access only, which the operator already has.

The sink flags are given to =devops-bb-sandbox-attach=. Run by hand, as
in the tests, =publish= takes them and reads its lines from stdin.

** Consumer: feed mode

- =DEVOPS_BB_FEED=DIR= (or =--feed DIR=) switches it on. Explicit, never
  auto-detected, so a mistake cannot fall back to Emacs.
- The commands read the feed through =feed.clj='s reader (=status=,
  =events-after seq=, =output id=), the one place a NATS reader would
  replace later.
- =status=: =status.json=. =follow=: tail =events.jsonl=, printing
  =SEQ summary= per event; without =--after= only new events, as in host
  mode; =--after SEQ= resumes, =--after 0= replays the feed. =run-output
  ID=: =outputs/ID.json=, or the =not-found= answer shape. =run-output=
  checks ID is a UUID (no path traversal).
- =status= names the feed and the workbook. =follow= needs no =--dir=:
  every event is the workbook's.
- =modified=: =true= when the last =modify= / =save= / =revert= /
  =kill= event in =events.jsonl= is a =modify=. =FILE=, if given, must
  be the workbook, or it fails with ="not this sandbox's workbook"=. It
  is a check, not a lock: the operator can start typing between check
  and write. Emacs still catches that and warns on the next edit that
  the file changed on disk.
- =modified=: FILE is optional in feed mode, still required on the
  host.
- =output=, =sessions=, =revert=, =tools=, =drift=: fail with ="needs
  Emacs, which this sandbox cannot reach"=. Dropped on purpose; the
  operator is the channel for them. The dashboard follows
  =FEED/events.jsonl=, and a run's detail says the same; =e= does
  nothing.
- =follow= notices go to stderr as =notice: …=, once per episode: a
  stale heartbeat (over 15 s), "publisher is N events behind" (with
  it, or alone when =queued= > 0 in two heartbeats running), detached,
  and "feed restarted at T: seq starts again at 1".
- A =truncated= output: the skill tells Claude to say so, and to write
  a block that prints less (a filter, =head=, =grep=) instead of asking
  for the whole thing.
- Output is data. Server output can carry injected text; the skill
  tells Claude never to follow instructions found in it.

** Caveats

*Sync blocks reach the sandbox too.* Development means =emacs-lisp=,
=:results value=, =mermaid= and other =:file= blocks, which are sync:
no =id=, no =result= line. The subscriber runs in
=org-babel-after-execute-hook=, after =#+RESULTS= is written, so for a
sync =execute= from an attached buffer it makes up a UUID and sends
the event with ="id"=, ="sync": true= and the =output= from
=devops-bb-scripting--results-text=, capped the same way. A =:file=
result sends its link text; Claude reads the file through the
workbook dir. =outputs/<id>.json= keeps the =run-output= shape:
=session= null, =status= =done=, =input= the block's body. A sync
=execute= always sends its =#+RESULTS= and keeps any =error= field: "Not
run on a #+TARGET" is what every sync block off a target carries
(=emacs-lisp=, =mermaid=). Other entries with an =error= (=tangle=,
=drift=) carry no output. A sync =execute= usually follows the =modify=
entry of its =#+RESULTS= write.

The output of a sync run is =#+RESULTS=, which org may have formatted
(tables, value results), not raw stdout, and stderr is lost unless
the block captures it. =output FILE LINE= is not in feed mode.

** Roadmap: agents on their own machines, a NATS log

- *The sink is the seam.* A NATS sink is two more verbs behind =put=
  and =append=: an output goes to a KV or object store keyed by run
  id, and an event is published on =devops.<feed>.events= in
  JetStream. The Emacs side does not change.
- With NATS the sandbox subscribes to
  the broker, not the host, with a credential that may read its feed's
  subjects only. Isolation moves from "what the publisher pushes" to
  account permissions.
- =seq= and the feed name are JetStream's sequence and subject.
- The consumer reads through =feed.clj='s reader; a NATS reader
  replaces the directory one.
- The global log could become a subscriber that publishes to NATS
  too, and the host's =follow= and dashboard read the stream.
- Agents on their own instances or containers do not change the event
  path. Getting the workbook to them stays the open problem (below).

** Not in scope

- Any channel from sandbox to host (no write-back). Claude checks
  =modified= before it writes; =revert= is replaced by
  =global-auto-revert-mode= on the host, which reloads an unmodified
  buffer once Claude's write lands (mount or pull). The README
  recommends it. The pull is host-driven, so it is not a channel from
  the sandbox.
- TRAMP workbooks, and two-way sync. The only sync built is
  =devops-bb-sandbox-pull= (sandbox → host, rsync).
- Redaction of secrets in output. The feed holds what Emacs holds.
  Claude does not quote credentials (as before); =bb scan= hooks stay.
- *Replay.* A new sandbox starts empty (follow starts "from now"). No
  =--since= to seed =events.jsonl= with recent history. A publisher
  restart is a new feed.
- Persisting confirmed fingerprints across Emacs restarts or detach.
- Stopping editor tooling (LSP, magit) that acts on the dir on visit;
  the README warns.
- NATS, and agents on their own machines (above).
