* Background

Business reason: we work with servers and systems containing sensitive data.
Users have a significant access scope via CLIs and Tailscale SSH.

Best practices for security dictate that agents should be running in a
sandbox, where they cannot access the user's file system or other
credentialed services.  "Sandboxes" and other controls built into
agent harnesses are fragile, and the agent can overcome them easily.

We believe the only way to run agents is in a separate machine or container.
Here, the agent writes files, runs local tools (in the sandbox, for example
finding a pattern using grep.)

When the agent needs something from the outside world, it should ask the user to
run a command. Copying and pasting commands and results is a terrible workflow,
especially in demanding situations like an incident, when we may be running dozens
of code blocks to find root cause.

Our approach leverages Emacs's org mode and its org-babel executable notebooks.
Devops.el contains some basic primitives like =TARGET= selection and logging.

This project implements a more highly opinionated flow using babashka tasks.
We would like to use this as a dependency in other projects' =bb.edn= tasks.

* Spec

** Goal

Claude Code runs in a *sandbox* and still works the devops-bb loop:

- it writes and edits workbooks;
- the operator runs the blocks in Emacs, on the host;
- Claude follows each run and reads its output;
- it *never* executes anything on the servers, and holds nothing that
  could reach the host's Emacs or the servers.

The sandbox is any place Claude can be put, not only a devcontainer:

| Sandbox                           | Workbook reaches it by      | Feed reaches it by            |
|-----------------------------------+-----------------------------+-------------------------------|
| local container                   | bind mount (rw)             | bind mount (ro) of the feed   |
| Tailscale node / SSH box          | git, rsync, or Emacs TRAMP  | host pushes over ssh          |

The workflow is the library's main one, so the design bends devops.bb
to it instead of wrapping it with scripts in each project
(replaces steps 4-5 of the infra-devcontainer workbook).

** The one idea

devops.bb today answers from two sources on the host: the execution
log (a file) and Emacs (=emacsclient=). The sandbox can reach neither.

So split devops.bb along that line:

- *producer*, on the host: =devops-bb export= turns "log + Emacs" into
  a *feed*, a self-contained directory of plain files, and publishes it
  to a *sink*.
- *consumer*, in the sandbox: with =DEVOPS_BB_FEED=DIR=, the same
  commands (=status=, =follow=, =run-output=, =output=) read the feed.
  They never start =emacsclient=.

Data flows one way, host → sandbox. The sandbox has no credential for
the host. That is the whole security argument; every choice below
keeps it.

** The feed

#+begin_example
FEED/
  status.json         devops-mode, execution-log, exporter heartbeat
  events.jsonl        the log lines, paths mapped, appended in order
  outputs/<id>.json   run-output answer, one file per finished async run
  outputs/<file>@<line>.json   latest output of a sync block (see Open questions)
#+end_example

Rules for the exporter:

1. *Output before event.* Write =outputs/<id>.json= first, append the
   =result done= line to =events.jsonl= after. A consumer that sees the
   event can read the output at once, so there is no =not-found= retry.
2. *Atomic.* Write to =.tmp=, rename. =events.jsonl= is append-only.
3. *Heartbeat.* =status.json= carries =exporter-time=, refreshed
   every few seconds, so the sandbox can tell a quiet log from a dead
   exporter.
4. *Path mapping.* =--map HOST=SANDBOX= rewrites =file= (and =buffer=
   stays). Log paths are host paths; a sandbox that mounts elsewhere
   still resolves =follow --dir= and =output FILE LINE=. Same absolute
   path (no =--map=) remains the easy case for containers.

** Sinks: where the feed goes

One verb, =put(path, bytes)=, and one option, =--via=:

| Sink                  | Flags                                          |
|-----------------------+------------------------------------------------|
| local directory       | =--to /path/feed= (dev and tests; no isolation by itself) |
| container (mount)     | =--to /path/feed=, mount that dir ro           |
| container (no mount)  | =--via "docker exec -i box" --to /feed=        |
| Tailscale / SSH node  | =--via "ssh node" --to /home/me/feed=          |

With =--via CMD=, a put runs =CMD sh -c 'cat > F.tmp && mv F.tmp F'=
(append: =cat >> F=). Anything that runs a command somewhere fits:
=ssh=, =tailscale ssh=, =docker exec -i=, =podman exec -i=, =kubectl
exec -i=. No TRAMP re-implementation; the operator's own ssh config and
Tailscale ACLs decide who may be reached.

Why push, not pull: a pull would give the sandbox a way into the host.
Push needs host → sandbox access only, which the operator already has.

** Consumer: feed mode

- =DEVOPS_BB_FEED=DIR= (or =--feed DIR=) switches it on. Explicit, never
  auto-detected, so a mistake cannot fall back to Emacs.
- =status=: =status.json=. =follow=: tail =events.jsonl=.
  =run-output ID=: =outputs/ID.json=, or the =not-found= answer shape.
  =run-output= checks ID is a UUID (no path traversal).
- =output FILE LINE=: sync blocks only, from =outputs/<file>@<line>.json=
  (or dropped; see Open questions).
- =sessions=, =modified=, =revert=, =tools=, =drift=, =dashboard's
  Emacs views=: fail with ="needs Emacs, which this sandbox cannot reach"=.
  Dropped on purpose; the operator is the channel for them.
- =follow= in feed mode warns once when =exporter-time= is stale.

** Not in scope (v1)

- Any channel from sandbox to host (no write-back, no "modified" flag).
  Rule stays: operator saves the workbook before Claude writes it, and
  reverts the buffer afterwards.
- Getting the *workbook* to a remote sandbox. Name the three ways
  (mount, git, TRAMP) in the README; do not build sync.
- Redaction of secrets in output. The feed holds what Emacs holds.
  Claude does not quote credentials (as before); =bb scan= hooks stay.

** Open questions

1. *Sync blocks.* They log =execute= with no id and no =result=. Is the
   line written before or after the block finishes? (Step 2 finds out.)
   If after: exporter calls =output FILE LINE= on the =execute= line and
   keys by =file@line=. If before: poll with backoff, or tell operators
   to use =:results output= (async) in sandboxed workbooks. The latter
   is simpler and I lean to it.
2. *Several sandboxes at once.* Allowed: one =export= process per sink.
   Each tails the log independently. Nothing shared.
3. *Replay.* A new sandbox starts empty (follow starts "from now"). Do we
   want =--since= to seed =events.jsonl= with recent history? Probably
   =export --backfill N= for the last N events.
4. *Dashboard.* Works on the feed for the feed view; the detail view
   needs Emacs. Leave as is in v1.
5. *Name.* =export= vs =feed= vs =publish=.

** Done when

- =devops-bb export --dir D --to FEED= on the host fills a feed as the
  operator runs blocks.
- With =DEVOPS_BB_FEED=FEED= and *no Emacs reachable* (no socket, no
  =emacsclient= on PATH), =status=, =follow= and =run-output= answer, and
  the others fail with the message above.
- The same feed works for: a local dir, a container with a ro mount,
  a container with =--via "docker exec -i"=, and a Tailscale node with
  =--via "ssh node"=.
- Tests in =devops.bb.cli-test= / a new =feed-test= cover feed mode and
  assert that no =emacsclient= process starts.
- =skills/devops-bb/SKILL.md= and README describe feed mode and its
  limits.
- The infra-devcontainer workbook shrinks to =.devcontainer= config and
  a =devops-bb export= line.
